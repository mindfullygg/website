# Mindfully.gg Skills

One folder per role. Folders are named by **role**, never by agent name —
creators assign their own Minds and name them whatever they like, so a Skill
that says "you are Vera" is broken for every creator who called theirs
something else.

### Bazaar names

All five publish under one prefix so they cluster together in a listing:

| Folder | Bazaar name |
| --- | --- |
| moderator | `Mindfully_Moderator` |
| trust-keeper | `Mindfully_Trust_Keeper` |
| culture-learner | `Mindfully_Culture_Learner` |
| community-guide | `Mindfully_Community_Guide` |
| health-pulse | `Mindfully_Health_Pulse` |

Underscores match the dominant convention on the Bazaar, and the single prefix
means all five sit together when someone browses.

Names are **role-based, never Keeper-based** — `Mindfully_Moderator`, not
`Mindfully_Kira`. A creator who named their Mind something else should not find
a stranger's name in their listing.

The name is only the listing. The **description** is what makes a Mind invoke
the Skill, so that is where the effort belongs — and it is the right place for
the word "Vigil", e.g. *"Turns this Mind into the moderator Vigil for one
community…"*

| Folder | Alias (stable handle) | Code parses its output? |
| --- | --- | --- |
| [moderator](moderator/) | `kira-mod` | **Yes** — classification, action, confidence |
| [trust-keeper](trust-keeper/) | `vera-trust` | **Yes** — trust score |
| [culture-learner](culture-learner/) | `sage-culture` | No |
| [community-guide](community-guide/) | `nova-onboard` | No — output is sent to a member verbatim |
| [health-pulse](health-pulse/) | `mira-health` | No |

## What is in this folder, and what is not

Each role folder holds its contract (`README.md`), its machine-checked test
cases (`fixtures.json`), and for roles that have been worked on, a status report
and notes.

**`SKILL.md` — the Skill body itself — is deliberately absent.** The contract it
has to satisfy is public, the fixtures that verify it are public, and the prompt
each role actually receives is public in
[lib/orchestrator.ts](../lib/orchestrator.ts). Only the authored wording is held
back.

Also not committed: `.runs/` (raw replies from live eval runs) and `prompts.txt`
(generated by `--dry`; regenerate rather than commit, or it goes stale the way a
hand-copied prompt file does).

The harness that scores all of this is
[scripts/eval-skill.ts](../scripts/eval-skill.ts).

## How addressing works

`provisionSwarm` in [lib/minds-client.ts](../lib/minds-client.ts) calls
`ensureConversation(alias, mindId)`, binding our stable alias to whichever Mind
the creator assigned. Every later call addresses the alias. **The Mind's own
name never appears anywhere in the code path.**

The Minds also never talk to each other. The orchestrator queries them and
injects the replies into the next prompt, so no Skill needs to name a peer.
Refer to injected context by the labels the orchestrator uses — `TRUST CONTEXT`,
`CULTURAL CONTEXT` — which are ours and stable.

## Rules for every Skill

1. **No proper names.** Define the role. Never assume what the Mind is called.
2. **Honour the output contract** where one exists. That is what the code
   depends on; prose quality is secondary to being parseable.
3. **Degrade gracefully on cold start.** A new community has no history. The
   Skill must still produce a well-formed answer about a member it has never
   seen, rather than hedging in prose.
4. **No preamble.** Don't open with "Sure, here's my assessment".

## Build order

moderator → trust-keeper → culture-learner → community-guide → health-pulse.

The moderator goes first because the eval cans upstream context, so it can be
tuned without the others existing — and its fixtures then become the written
spec for what the trust and culture roles must produce.

## Building and publishing

Skills are built **conversationally**, not by pasting into an editor. You
describe the Skill to your Mind and it assembles the four underlying artifacts —
Registry Offering (the listing), App Manifest (app wiring), Tool Schemas
(permitted actions), Skill Playbook (behaviour) — none of which you write
directly.

The flow is: describe → refine → connect → run → inspect → publish.

**Connect does not apply to us.** These Skills take text in and return text.
They need no App Manifest and no Tool Schemas. If a Mind attaches tool access
while building one, that is unrequested attack surface — tighten it before
publishing.

**Always run the inspect step before publishing:**

```
Show me what this Skill can do, what it reads, and what it can change.
Flag anything it should not touch.
```

For these roles the correct answer is essentially "nothing" — no external reads,
no external writes. Anything else needs explaining.

**Publish with a message, not a portal:**

```
Publish this Skill to the Bazaar as "Mindfully_Moderator"
so other Minds can equip it.
```

Then put the resulting skill id in
[lib/skills-config.ts](../lib/skills-config.ts). `provisionSwarm` equips it on
setup; the equip step no-ops while the id list is empty.

**When describing a Skill, say that the format is literal.** The Mind builds
from your description and may reword it. For the moderator that breaks the
anchored parser and escalates everything; for the community guide it reintroduces
the preamble that gets DM'd to a member. Verify with a dry run either way.

## Evaluating

Four stages, cheapest first. The first three cost nothing.

**0 — Does your intended format even parse?** Write the reply you want by hand
and check it before any Mind is involved.

```
npx tsx --env-file=.env.local scripts/eval-skill.ts skills/moderator/fixtures.json \
  --case clear-scam-shill --check-reply my-intended-reply.txt
```

**1 — Dry.** Shows the exact prompts and runs the pre-filter cases.

```
... skills/moderator/fixtures.json --dry
```

**2 — Isolated, live.** One call per case against one Mind, with upstream
context canned. Reports which Skills are equipped and how much cognition the
run cost.

```
... skills/moderator/fixtures.json --mind <mindId> --fresh
```

**Use `--fresh` after every Skill edit.** A conversation carries memory, so
re-running a fixture in the same conversation means the Mind sees its own
earlier answers — a "fix" can look like it worked when the Mind is only
remembering being corrected.

**3 — Integrated.** Post in a real community and let the full chain run. When
something looks wrong here, read `veraContext` / `sageContext` on the stored
escalation to see exactly what the moderator was given — that separates a Skill
problem from a wiring problem.

Re-scoring is free: `--replay skills/<role>/.runs/<file>.json`. Most iteration
is scoring iteration, so reach for this before spending another call.
